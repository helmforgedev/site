# OpenSign

[OpenSign](https://www.opensignlabs.com) is an open-source electronic-signature
platform. The HelmForge chart deploys the official OpenSign v2.41.3 frontend
and backend with HelmForge MongoDB, durable document storage, stable identity,
and production-oriented Kubernetes defaults.

The chart is stable. The backend remains a singleton because upstream performs
migrations during startup; the stateless frontend starts with two replicas and
can scale independently.

## What this chart provides

- official frontend and backend images pinned by immutable manifest digest;
- separate frontend and Parse API Deployments, Services, Ingresses, and routes;
- HelmForge MongoDB 1.8.6 or an external MongoDB URI;
- retained local document PVC or S3-compatible object storage;
- generated retained master key, existing Secret, and External Secrets modes;
- PKCS#12 signing, SMTP, and object-storage credential contracts;
- frontend HPA and PodDisruptionBudget with a migration-safe singleton backend;
- non-root UID/GID 1000, read-only roots, dropped capabilities, seccomp, and no
  mounted API token;
- component-aware NetworkPolicy and dual-stack Services.

## Install

```bash
helm repo add helmforge https://repo.helmforge.dev
helm repo update
helm install opensign helmforge/opensign \
  --version 1.0.0 \
  --namespace opensign \
  --create-namespace
```

The default deploys two frontend replicas, one backend, authenticated MongoDB,
a retained document PVC, and an automatically generated Parse master key.

## Image provenance

Upstream deployment channels are mutable. The chart records the v2.41.3 source
commit `e5f2c5c0a9f65ec01d8a53e4bf3a390c7ade7bcd` and pins the manifests resolved
on 2026-10-21:

```text
docker.io/opensign/opensign@sha256:0ebc230eed21ced0d321a0df887c1a48e9f4bd423c2454fe865a262aec49f99a
docker.io/opensign/opensignserver@sha256:cadfcaaa20bf40272aed43c91314362c1dac034b2a4651f50e5288d01c2b434d
```

Review the [official v2.41.3 release](https://github.com/OpenSignLabs/OpenSign/releases/tag/v2.41.3)
before changing both digests together.

## Configure public URLs

OpenSign needs a browser-visible frontend origin and Parse API URL. The API URL
must end in `/app`:

```yaml
config:
  publicUrl: https://sign.example.com
  apiUrl: https://sign-api.example.com/app
```

Use distinct hosts because the backend exposes root-level Parse routes in
addition to `/app`. Ingress and Gateway API are mutually exclusive.

## Protect identity and signing keys

Production GitOps installations should provide a stable Secret:

```yaml
secrets:
  existingSecret: opensign-production
  masterKeyKey: master-key
  pfxBase64Key: pfx-base64
  pfxPassphraseKey: pfx-passphrase
  smtpPasswordKey: smtp-password
```

The PFX value contains a base64-encoded PKCS#12 certificate. Configure it and
its passphrase together. Back up the master key, certificate, and integration
credentials independently of the Helm release.

## Use S3-compatible storage

```yaml
storage:
  type: s3
  s3:
    bucket: opensign-documents
    endpoint: https://s3.example.com
    baseUrl: https://documents.example.com
    region: us-east-1

secrets:
  existingSecret: opensign-production
```

The public base URL must be reachable by browsers retrieving documents. Grant
the credentials only the object operations required for the selected bucket.

## Use external MongoDB

```yaml
mongodb:
  enabled: false
externalMongodb:
  enabled: true
  existingSecret: opensign-mongodb
  existingSecretUriKey: mongodb-uri
  networkPolicyPeers:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: database
```

The URI should include TLS, replica-set, authentication database, and other
provider-specific parameters. With NetworkPolicy enabled, declare a precise
`networkPolicy.extraEgress` rule for private MongoDB endpoints.

## External Secrets

```yaml
secrets:
  existingSecret: opensign-production

externalSecrets:
  enabled: true
  secretStoreRef:
    name: production
    kind: ClusterSecretStore
  items:
    - secretKey: master-key
      remoteRef:
        key: opensign/production
        property: master-key
    - secretKey: pfx-base64
      remoteRef:
        key: opensign/production
        property: pfx-base64
    - secretKey: pfx-passphrase
      remoteRef:
        key: opensign/production
        property: pfx-passphrase
```

The required master-key mapping is validated before installation. Add SMTP and
S3 mappings when those integrations are enabled.

## Availability and upgrades

The frontend defaults to two replicas with a PodDisruptionBudget. Enable HPA
only when Kubernetes resource metrics are available:

```yaml
frontend:
  autoscaling:
    enabled: true
    minReplicas: 2
    maxReplicas: 5
    targetCPUUtilizationPercentage: 70
```

The backend deliberately uses one replica and `Recreate` updates. Schedule a
brief API interruption, back up state first, and do not override this topology
without upstream evidence that migrations are concurrency-safe.

## Backup and restore

Protect MongoDB, the local PVC or S3 bucket, the master key, signing
certificate, and integration credentials as one recovery set. Restore the same
image digests into an isolated namespace and verify login, an existing
template, upload, signing, download, and email before upgrading production.

## Uninstall

```bash
helm uninstall opensign --namespace opensign
```

The chart-created document PVC is retained by default. Confirm MongoDB and
documents are backed up before removing any retained volume or external bucket.
