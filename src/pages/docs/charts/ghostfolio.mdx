# Ghostfolio

[Ghostfolio](https://ghostfol.io) is an open-source wealth-management application for tracking portfolios, holdings,
activities and net worth. The HelmForge chart deploys the official Ghostfolio image with PostgreSQL, Redis and
security-oriented Kubernetes defaults.

The chart is beta. Ghostfolio performs database migrations, seed work and scheduled portfolio jobs in the application
process, so this release deliberately runs one replica with a `Recreate` rollout.

## What this chart provides

- official `docker.io/ghostfolio/ghostfolio:3.82.0` release image;
- maintained PostgreSQL and Redis dependencies, with contracts for externally managed services;
- upstream-native startup, liveness and dependency-aware readiness probes;
- retained application identity, existing Secret support and native External Secrets Operator resources;
- optional experimental OIDC authentication;
- opt-in Ingress or Gateway API exposure;
- non-root execution, read-only root filesystem, dropped capabilities and no mounted API token;
- product-aware NetworkPolicy, dual-stack Service and standard scheduling controls.

The chart does not claim application-level horizontal scaling, Prometheus metrics or automated backups because those
contracts are not documented by upstream.

## Install

```bash
helm repo add helmforge https://repo.helmforge.dev
helm repo update
helm install ghostfolio helmforge/ghostfolio \
  --namespace ghostfolio \
  --create-namespace
```

The default installation deploys PostgreSQL and Redis with persistent volumes. The first account registered in a new
Ghostfolio instance becomes its administrator. Keep external exposure private until that registration is complete.

## Understand the pinned image

The default image is the official Ghostfolio `3.82.0` release. Its manifest was verified for Linux `amd64`, `arm/v7`
and `arm64`. Changing `image.tag` remains available for a reviewed upgrade or private mirror.

## Expose the application

Ingress and Gateway API support are opt-in and mutually exclusive. Set the canonical public origin explicitly in
production so generated links and OIDC callbacks are stable:

```yaml
ghostfolio:
  rootUrl: https://portfolio.example.com
  trustProxy: '1'

ingress:
  enabled: true
  ingressClassName: nginx
  hosts:
    - host: portfolio.example.com
      paths:
        - path: /
          pathType: Prefix
  tls:
    - secretName: portfolio-tls
      hosts:
        - portfolio.example.com
```

The chart can derive `ROOT_URL` from the first Ingress host or HTTPRoute hostname, but an explicit HTTPS value avoids
ambiguity. Set `ghostfolio.trustProxy` only to the trust policy required by the selected ingress path.

## Use managed PostgreSQL and Redis

For production, disable the bundled services and reference credentials held in Kubernetes Secrets. Database URLs must
be complete and URL-encoded because this avoids exposing passwords in Helm values or assembling unsafe connection
strings in templates.

```yaml
postgresql:
  enabled: false
database:
  external:
    enabled: true
    existingSecret: ghostfolio-database
    urlKey: database-url
    directUrlEnabled: true
    directUrlKey: direct-url
    host: postgres.database.svc.cluster.local
    networkPolicyPeers:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: database

redis:
  enabled: false
  external:
    enabled: true
    host: redis.cache.svc.cluster.local
    existingSecret: ghostfolio-redis
    passwordKey: redis-password
    networkPolicyPeers:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: cache
```

Use `DIRECT_URL` when migrations must bypass a transaction pooler. Both service hosts are also used by the dependency
wait containers. Configure matching NetworkPolicy peers for private destinations.

## Preserve application identity

The chart creates and retains random values for `ACCESS_TOKEN_SALT` and `JWT_SECRET_KEY` by default. For deterministic
GitOps or recovery, create a Secret containing `access-token-salt` and `jwt-secret-key`, then set
`ghostfolio.existingSecret`. Rotating either value invalidates authentication material.

Market-data provider credentials can be supplied with `ghostfolio.extraEnv` using `valueFrom.secretKeyRef`, or through
`ghostfolio.extraEnvFrom`. Do not store credentials directly in values files.

## Configure OIDC

Ghostfolio marks OIDC as experimental. Register the callback
`https://portfolio.example.com/api/auth/oidc/callback`, store the client secret separately, and configure:

```yaml
ghostfolio:
  rootUrl: https://portfolio.example.com
oidc:
  enabled: true
  issuer: https://identity.example.com/realms/portfolio
  clientId: ghostfolio
  existingSecret: ghostfolio-oidc
  clientSecretKey: client-secret
  scopes:
    - openid
    - profile
    - email
```

Test login, logout, callback routing and account mapping with the pinned Ghostfolio version before depending on OIDC in
production.

## Materialize Secrets with External Secrets Operator

`externalSecrets.items` accepts native ExternalSecret specifications. The operator and a SecretStore or
ClusterSecretStore must already exist. This example supplies application identity:

```yaml
externalSecrets:
  enabled: true
  items:
    - name: application
      fullnameOverride: ghostfolio-application
      spec:
        secretStoreRef:
          name: production-secrets
          kind: ClusterSecretStore
        target:
          name: ghostfolio-application
        data:
          - secretKey: access-token-salt
            remoteRef:
              key: ghostfolio/application
              property: access-token-salt
          - secretKey: jwt-secret-key
            remoteRef:
              key: ghostfolio/application
              property: jwt-secret-key
ghostfolio:
  existingSecret: ghostfolio-application
```

Use the same contract for OIDC, database, Redis and provider credentials.

## Health and operations

Startup and liveness use `/api/v1/health/liveness`, which does not couple process restarts to PostgreSQL or Redis
outages. Readiness uses `/api/v1/health` and withdraws traffic when either dependency is unavailable. Keep the readiness
timeout at five seconds or longer because the upstream Redis check can consume that interval.

The application waits for both TCP listeners, then its official entrypoint runs Prisma migrations and seed work before
starting the NestJS server. Keep `replicaCount=1`; use one Helm release per independent Ghostfolio instance.

## Network policy

The default policy allows namespace-local HTTP ingress, DNS, the bundled PostgreSQL and Redis workloads, and public
HTTP/HTTPS egress for market-data providers. Public egress excludes private and special-use ranges. External private
services require `database.external.networkPolicyPeers`, `redis.external.networkPolicyPeers` or explicit
`networkPolicy.extraEgress` rules.

If an ingress controller runs in another namespace, add its namespace and pod selectors to `networkPolicy.ingressFrom`.

## Back up and recover

PostgreSQL is the system of record. Redis persistence helps cache continuity but is not a substitute for a PostgreSQL
backup. The chart is marked `backup: false` because it does not ship an automated end-to-end backup controller.

Before an upgrade, create a transactionally consistent PostgreSQL backup, preserve the application Secret and record
the chart and image versions. Restore into an isolated namespace and verify login, holdings, account history and a
provider refresh before declaring the recovery procedure successful.

## Uninstall

```bash
helm uninstall ghostfolio --namespace ghostfolio
```

Confirm the retention and backup state of PostgreSQL and Redis PVCs before uninstalling. Kubernetes and the storage
provisioner control PVC lifecycle after removal.
