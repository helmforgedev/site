# IB Gateway

[IB Gateway Docker](https://github.com/gnzsnz/ib-gateway-docker) packages Interactive Brokers Gateway with IBC, Xvfb,
and TCP proxies. The HelmForge chart deploys that community-maintained runtime as a private singleton with safe paper
defaults, immutable image pinning, Secret-backed credentials, persistent settings, and product-aware probes.

The image is not published by Interactive Brokers. HelmForge and the image project are not affiliated with or endorsed
by Interactive Brokers. The image includes proprietary IB Gateway software, and operators remain responsible for all
IBKR agreements, permissions, subscriptions, and trading controls.

## What this chart provides

- `ghcr.io/gnzsnz/ib-gateway:10.50.1f` pinned by immutable amd64 and arm64 manifest digest;
- paper trading, read-only API, blind trading disabled, VNC disabled, and ClusterIP exposure by default;
- exactly one Deployment replica with `Recreate` upgrades to prevent overlapping account sessions;
- managed Secret, existing Secret key mapping, and External Secrets Operator resources;
- password-file projection through upstream `_FILE` variables;
- persistent TWS settings with retained PVC support;
- live, paper, or simultaneous Service port mapping;
- internal-listener readiness checks and conservative process liveness;
- NetworkPolicy, dual-stack Services, scheduling controls, and baseline Pod hardening.

The IBKR API is raw TCP without chart-provided authentication or encryption. The chart intentionally does not create
Ingress or Gateway API resources.

## Install for paper trading

Create a mode-`0600` password file outside the repository, then create the credential Secret without putting the
password in shell history:

```bash
kubectl create namespace ib-gateway
kubectl -n ib-gateway create secret generic ib-gateway-credentials \
  --from-literal=username='your-paper-username' \
  --from-file=password=/secure/path/ibkr-password
```

Protect that temporary file and remove it securely after confirming the Secret exists.

Install the chart:

```bash
helm repo add helmforge https://repo.helmforge.dev
helm repo update
helm install ib-gateway helmforge/ib-gateway \
  --version 1.0.0 \
  --namespace ib-gateway \
  --set auth.existingSecret=ib-gateway-credentials
```

Watch the logs and approve the expected mobile two-factor request:

```bash
kubectl -n ib-gateway logs deployment/ib-gateway --follow
kubectl -n ib-gateway rollout status deployment/ib-gateway
```

## Connect a paper client

Keep the Service internal. For temporary workstation access:

```bash
kubectl -n ib-gateway port-forward service/ib-gateway 4002:4002
```

Connect the client to `127.0.0.1:4002`. The live API uses Service port 4001. The container internally proxies those
ports through 4004 and 4003 respectively, matching the upstream image contract.

Set `networkPolicy.apiIngressFrom` to explicit namespace or Pod selectors when clients run elsewhere in the cluster.
Use a private encrypted network for any path outside the cluster. Never expose the Service directly to the internet.

## Manage credentials

The existing Secret defaults to these keys:

| Mode                                    | Username key     | Password key     |
| --------------------------------------- | ---------------- | ---------------- |
| Live or paper                           | `username`       | `password`       |
| Additional paper session in `both` mode | `paper-username` | `paper-password` |

Override the `auth.*Key` values when your secret manager uses different names. Passwords are mounted as files;
usernames use `secretKeyRef` because upstream does not expose username-file variables. Inline credential values exist
only for evaluation and are stored in Helm release history.

External Secrets can materialize the exact Secret consumed by the Deployment:

```yaml
auth:
  existingSecret: ib-gateway-credentials
externalSecrets:
  enabled: true
  items:
    - fullnameOverride: ib-gateway-credentials
      spec:
        secretStoreRef:
          name: production
          kind: ClusterSecretStore
        data:
          - secretKey: username
            remoteRef:
              key: trading/ibkr/username
          - secretKey: password
            remoteRef:
              key: trading/ibkr/password
```

Credential rotation ends the current session and usually requires fresh two-factor approval. Coordinate rotation with
trading operations and restart the singleton Deployment after the target Secret synchronizes.

## Understand readiness

The public container listeners belong to `socat` and can start before authentication finishes. With credentials
configured, startup and readiness inspect the active internal Gateway listener instead. An empty evaluation install
only checks that the credential-waiting process runs; its Service is not usable.

Readiness does not prove that an account can place orders, that market data is subscribed, or that IBKR services are
healthy. Monitor those domain conditions from the trading client.

## Enable live trading deliberately

Use paper trading first. Before changing `gateway.tradingMode` to `live`:

1. Verify the intended account Secret and two-factor device.
2. Prove client behavior and reconnect handling against paper trading.
3. Keep `gateway.readOnlyApi: true` until write access is separately approved.
4. Review `gateway.allowBlindTrading`; the safe default is false.
5. Confirm NetworkPolicy and private transport restrict every API client.

The chart does not implement order limits, reconciliation, or trading-risk policy.

## Persist and recover settings

The default PVC stores `/home/ibgateway/tws_settings`. It does not store credentials, account state, or generated IBC
configuration. Back up customized settings with your storage platform and test recovery in an isolated paper-trading
release.

A persisted `jts.ini` can retain the initial timezone. Changing `gateway.timeZone` may therefore require a deliberate
backup and cleanup of that setting so upstream can regenerate it.

## Use VNC for maintenance

VNC is disabled by default. When visual diagnostics are necessary, enable `vnc.enabled`, supply a Secret-backed
password, and use `kubectl port-forward` to the separate VNC Service. Keep it private and disable it after maintenance.

## Operational limitations

- IBC was retired by its maintainers on 2026-09-01 and receives limited maintenance.
- Concurrent sessions do not provide safe horizontal availability; the chart rejects multiple replicas.
- A `Recreate` upgrade intentionally introduces downtime and can require two-factor approval.
- No documented Prometheus endpoint exists, so the chart does not publish a misleading ServiceMonitor.
- IBKR endpoints can change, so egress isolation requires an operator-maintained gateway or allowlist.

## Uninstall

```bash
helm uninstall ib-gateway --namespace ib-gateway
```

The generated settings PVC is retained by default. Confirm backup and remove it separately only when the settings are
no longer required.
