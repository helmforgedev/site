# ArchiveBox

Self-hosted web archiving platform. ArchiveBox captures websites in multiple formats simultaneously — HTML,
PDF, screenshot, WARC, media extraction, git clone — using a built-in Chromium headless browser. All archived
content is stored on a persistent volume, with SQLite by default or optional
external PostgreSQL for metadata.

<Callout type="warning" title="Single instance only — no horizontal scaling">
  ArchiveBox uses one collection writer even with PostgreSQL. The chart enforces a single Recreate Deployment; do not
  scale it horizontally.
</Callout>

## Key Features

- **Multi-format archiving** — HTML, PDF, screenshot, WARC, media, git clone in one pass
- **Chromium headless** — full JavaScript rendering with `/dev/shm` tmpfs for stability
- **SQLite or PostgreSQL** — embedded SQLite or an existing PostgreSQL service
- **Access control** — public index/add controls and upstream UI snapshot permissions
- **Upstream privilege drop** — starts as root, detects collection ownership, then drops privileges
- **S3 backup** — `/data` archives with Secret credentials or workload identity
- **Persistent storage** — one PVC for archived content and SQLite when selected

## Architecture and boundaries

One Recreate Deployment owns the complete `/data` dataset: SQLite, indexes,
configuration, and captured artifacts. The optional backup CronJob reads that
same claim and uploads a volume archive to S3-compatible storage. Never run two
writers against the claim, even when the StorageClass supports ReadWriteMany.

The chart owns Kubernetes workload, storage, routing, credentials, and optional
backup resources. TLS policy, capture-egress controls, malicious-content
isolation, storage lifecycle, off-cluster retention, and monitoring remain
platform responsibilities. Review the
[complete design](https://github.com/helmforgedev/charts/blob/main/charts/archivebox/DESIGN.md)
for the Mermaid topology, security and observability boundaries, gaps, and
explicit non-goals.

## Installation

**HTTPS repository:**

```bash
helm repo add helmforge https://repo.helmforge.dev
helm repo update
helm install archivebox helmforge/archivebox -f values.yaml
```

**OCI registry:**

```bash
helm install archivebox oci://ghcr.io/helmforgedev/helm/archivebox -f values.yaml
```

### Persistence

The PVC stores the entire `/data` directory: SQLite database, all archived files (HTML, PDFs, screenshots, WARCs,
media), and ArchiveBox configuration. Size it generously — archived pages with media can consume gigabytes quickly.
Chart-created claims carry `helm.sh/resource-policy: keep`, so `helm uninstall` retains the dataset. Namespace deletion
and storage-provider retention policy can still remove it; use an existing claim when lifecycle must remain fully
outside Helm.

| Parameter                   | Type    | Default             | Description                                                 |
| --------------------------- | ------- | ------------------- | ----------------------------------------------------------- |
| `persistence.enabled`       | boolean | `true`              | Enable a PVC for `/data` (database + all archived content). |
| `persistence.size`          | string  | `50Gi`              | PVC size. Plan for 100GB+ for active archiving.             |
| `persistence.storageClass`  | string  | `""`                | StorageClass for the PVC.                                   |
| `persistence.accessModes`   | array   | `["ReadWriteOnce"]` | PVC access modes.                                           |
| `persistence.existingClaim` | string  | `""`                | Use an existing PVC instead of creating one.                |

<Callout type="warning" title="Storage must allow ownership changes">
  A narrowly scoped init container changes only a root-owned `/data` mount root to the selected UID/GID; it never
  recursively rewrites existing collections. Some NFS provisioners block `chown`, so configure the provisioner
  accordingly.
</Callout>

### Backup

The S3 backup archives `/data`. With SQLite, that includes the database and
archived files. With external PostgreSQL, the CronJob does not dump the
database; retain a matching `pg_dump` and quiesced `/data` archive.

`backup.enabled` requires `persistence.enabled: true`; the chart rejects an ephemeral backup configuration because the
CronJob must mount the durable data claim.

### Resources and Security

ArchiveBox uses Chromium internally to render pages. The Chromium process requires at least **2 GB RAM** to
function reliably. Without memory limits, the container may be OOMKilled during archiving of JavaScript-heavy
pages.

| Parameter            | Type   | Default                                        | Description                                                  |
| -------------------- | ------ | ---------------------------------------------- | ------------------------------------------------------------ |
| `resources`          | object | `{}`                                           | CPU and memory requests and limits. Recommended: 2–4 Gi RAM. |
| `podSecurityContext` | object | `{ seccompProfile: { type: RuntimeDefault } }` | Pod-level security context.                                  |
| `securityContext`    | object | Root startup with bounded capabilities         | Upstream entrypoint privilege-drop contract.                 |

The application container starts as root so the upstream entrypoint can detect
the collection owner and drop privileges. The default workload therefore needs
an explicit exception in namespaces enforcing Pod Security `restricted`.

## Common Issues

<Callout type="danger" title="Pod OOMKilled during archiving">
  Archiving JavaScript-heavy or media-rich pages triggers full Chromium rendering. Without explicit `resources` limits,
  the container may be OOMKilled. Set at least `memory: 2Gi` in `resources.requests` and `memory: 4Gi` in
  `resources.limits`. Monitor memory usage during peak archiving.
</Callout>

<Callout type="tip" title="Archiving times out on slow or complex pages">
  The default `archivebox.timeout` is 60 seconds. Pages with slow external resources or heavy JavaScript may time out
  before the snapshot is complete. Increase `timeout` to `120` or `180` for more reliable archiving of complex pages.
</Callout>
